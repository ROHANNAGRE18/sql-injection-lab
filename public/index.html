01 — Overview

What is SQL Injection?

SQL Injection occurs when untrusted user input is incorporated directly into SQL queries, allowing an attacker to manipulate the intended database operation — bypassing authentication, extracting data, or even destroying records. It remains one of the most critical web vulnerabilities according to the OWASP Top 10.

⚠️ Vulnerable Path

String Concatenation → Injection → Bypass

User input is inserted directly into the SQL string. Special characters can escape the intended context and modify the query structure — turning a login check into a tautology.

→Attacker enters: ' OR 1=1--
→String concat modifies query structure
→WHERE clause becomes always-true
→🚨 Authentication bypassed
🛡️ Secure Path

Parameterized Query → Input as Data → Blocked

User input is passed as a bound parameter, never as SQL syntax. The database driver handles serialisation; the query structure is fixed at parse time and cannot be changed by any input value.

→Same payload entered
→Input bound as data, not SQL
→Query structure unchanged
→🛡️ Attack blocked
02—Implementation

Vulnerable vs Secure Code

Both endpoints use the same database and accept the same inputs. The only difference is how user input is incorporated into the SQL statement — and that single difference determines whether the application is exploitable.

⚠️ Vulnerable Implementation

String Concatenation

User input is directly inserted into the SQL string. Special SQL characters — especially the single quote ' — can escape the string context and alter query logic.

Node.js / SQLite3 
// INTENTIONALLY VULNERABLE — EDUCATIONAL USE ONLY
// Input is concatenated directly into the SQL string.

const query = `SELECT * FROM users
  WHERE username = '${username}'
  AND password = '${password}'`;

db.get(query, callback);

When ' OR '1'='1 is entered as username, the query becomes:
...WHERE username = '' OR '1'='1' AND password = '' — the OR '1'='1' is always true, matching every row.

🛡️ Secure Implementation

Parameterized Query

Placeholders (?) mark where values will be bound. The database driver serialises input as data — the query structure is compiled before any user value is ever substituted.

Node.js / SQLite3 
// SECURE: parameterized query.
// Input is bound as data — never executable SQL.

const query = `SELECT * FROM users
  WHERE username = ?
  AND password = ?`;

db.get(query, [username, password], callback);

The same payload ' OR '1'='1 is treated as a literal string value. The database searches for a username equal to that whole string — which doesn't exist — so login is denied.

04—Attack Flow

How the Attack Works

A side-by-side view of what happens inside the application — from attacker input through to the database response — in both the vulnerable and secure scenarios.

🚨 Vulnerable Application Flow

🎯

Attacker Input

Username: ' OR 1=1--  / Password: (blank)

⚙️

String Concatenation

Input is directly embedded into the SQL string. The single quote closes the first string literal; OR '1'='1' becomes valid SQL appended to the query.

💀

Query Structure Modified

WHERE username = '' OR 1=1--' AND password = ''
The -- comments out everything after it. The OR 1=1 tautology makes the WHERE clause always true.

🗄️

Database Executes

All rows match. The first row (admin) is returned. No password was checked.

🔓

Unauthorized Access

The application believes authentication succeeded. The attacker is logged in as admin.

🚨 Authentication Bypassed — Unauthorized Access Granted

🛡️ Secure Application Flow

🎯

Attacker Input

Same payload: ' OR '1'='1

⚙️

Parameterized Query

The query template is compiled first: WHERE username = ? AND password = ?. The ? placeholders are filled in afterwards as data values.

🔒

Input Bound as Data

The driver serialises the payload as a string literal. No SQL characters from user input can alter the compiled query structure.

🗄️

Database Executes Safely

Searches for a username literally equal to ' OR '1'='1 — which does not exist in the table. Zero rows returned.

🛡️

Access Denied

No row matched — authentication fails. The attack has no effect.

🛡️ Attack Neutralized — Access Correctly Denied

06—Learning Outcomes

What You Learn

This lab is designed to build foundational knowledge of web application security, covering the attack, the root cause, and the correct defensive techniques.

💉

SQL Injection

SQL Injection occurs when user-supplied input is embedded in a query without sanitisation or parameterization, allowing an attacker to alter the query's intended logic. It is ranked in the OWASP Top 10 most critical web application security risks.

🔓

Authentication Bypass

A boolean injection payload such as ' OR '1'='1 appends a tautology (always-true condition) to the WHERE clause. Every row matches, so the first database user is returned — regardless of the password supplied.

🛡️

Prepared Statements

A prepared statement (parameterized query) separates SQL code from data. The query template is compiled by the database engine before user input is bound. User values cannot break out of their data context and alter query logic.

✍️

Secure Coding

The root cause of SQL Injection is trusting user input. The fix is to never incorporate raw user input into a SQL statement. Always use parameterized queries or an ORM that handles parameterization internally.

🔐

Defense in Depth

Parameterized queries are the primary defence against SQL Injection. Additional layers include:

  • Input validation and length limits
  • Least-privilege database accounts
  • Proper password hashing (bcrypt / Argon2)
  • Structured error handling — never expose raw DB errors
  • Application logging and anomaly monitoring
  • Regular security testing (SAST, DAST, penetration testing)
📋

OWASP & Standards

SQL Injection falls under A03:2021 — Injection in the OWASP Top 10. The OWASP SQL Injection Prevention Cheat Sheet recommends parameterized queries as the primary control, with stored procedures and allow-list input validation as supplementary defences.
